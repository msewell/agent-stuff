# SQL Server ingestion and reconciliation

Assume SQL Server with native non-null `rowversion`, a stable key within scope, and an approved read-only view. Confirm source identity, the connector’s session behavior, and supported snapshot isolation before adopting this protocol. Give the collector only the required source objects, columns, and scope; bind parameters through a private route. Prefer a background worker reading into a committed local projection rather than a connector call on the request path. Check what the connector spools.

## Delta and bootstrap protocol

`rowversion` orders allocations within a database incarnation, not commits or time. A low token can remain uncommitted while a higher token commits. Advancing to `@@DBTS` can skip the lower row forever. Store the token losslessly as fixed-width binary or hex, never as a JavaScript `number`. Track wall-clock lag separately. A long transaction elsewhere in the database can stall the safe fence.

1. Verify source incarnation, scope and mapping revision. Read the durable lower bound `L`, the first eligible token. On the same verified database capture `H = MIN_ACTIVE_ROWVERSION()` **before establishing the source snapshot**. A snapshot established before the fence could miss commits the later fence would cover.
2. Page through `L <= rv < H` in one consistent snapshot on a pinned session. Order by `(rowversion, stable key)` and page by that same lexicographic cursor; the ordering must be unique. Independent statement snapshots can drift even on one connection. If the connector cannot sustain one snapshot, use an approved, verifiably complete immutable export or another source mechanism with a documented consistency contract. Do not pretend independent pages are one observation.
3. Stage idempotently by scope, key, incarnation and token; do not overwrite a newer observation with a replay. If a row is invalid, block publication or record a durable invalid marker that yields `outage` for the key. Omission is not deletion.
4. Publish the staged work and set `L = H` in one local durable commit or equivalent recoverable barrier. Serialize publishers per scope or fence stale publishers. A crash before commit leaves the prior visible state and lower bound; after an ambiguous commit, reread the durable checkpoint. Never advance to an unscanned fence after a page limit or interrupted run.
5. If `H == L`, retain the checkpoint and track the stall. If `H < L` or identity, scope, or incarnation changes incompatibly, suspend and rebaseline. A restored database can overtake a previous numeric token, so a monotonic token is not proof of identity.

If bootstrapping a baseline plus rowversion deltas, capture a conservative fence before the consistent baseline; publish it with the staged projection and key set, then replay from the fence. If using full immutable exports alone, publish each verified export as a generation; no rowversion fence or delta replay is required. This is latest-state synchronization. Physical deletes, joined or filtered membership changes, and intermediate states are not reliably captured by a base row’s token. If every intermediate event or precise delete timing is required, use an approved committed change mechanism with operation metadata and cursor validity checks.

## Membership and replica reads

- Enumerate the whole approved key set in a consistent snapshot. Record source endpoint/role and incarnation, scope and filters, observation time, page progress and validated completion. Verify unique keys, coverage, and common canonical equality and sort order before comparing to a pinned local generation. A short final page can be valid under a verified enumeration contract; a short page or transport success alone is not proof where pages can be truncated.
- Treat `local − source` as candidates to retire from that scope, not proof of physical deletion. Apply only to the pinned generation or with a compare-and-swap guard that protects newer observations. For anomalous volume, scope drift, or incomplete evidence, hold removals; confirm a truly empty scope explicitly.
- Require acceptable source freshness independently of completeness. An Availability Group secondary can serve a complete but old snapshot even under synchronous commit: log hardening is not redo visibility. Queue size and a last-redone timestamp are diagnostics, not proof of what the scan saw. If using a secondary, establish progress using a trusted source reference and an approved, comparable marker observed inside the scan snapshot. Otherwise default to an approved primary route or authoritative immutable export.
- If the serving session is replaced, identity is uncertain, or recovery history is incompatible, discard the scan for publication. A lagging or unverified scan neither removes keys nor renews membership freshness. Keep the last verified positive only as freshness and authorization permit. A miss without usable prior membership evidence is `outage`, not `unknown-key`. Set scan cadence from maximum tolerated false presence, including execution, backlog and publication delay.

## Acceptance evidence

Use the actual SQL Server and connector topology in a safe environment. Hold a low-token transaction open, commit a higher token separately, verify the first scan defers the unsafe range, then commit the low token and verify it arrives without a checkpoint gap. Inject run interruption, rerouting and repeatable truncation; assert no checkpoint moves past published work and no prior keys are removed. On a lagging secondary, omit a newly committed primary key both with and without a verified local positive; assert the scan can neither remove the positive nor certify absence. Test reappearance between scan and publication, restore/rebaseline, and a crash or uncertain local commit. Verify the published generation and checkpoint together.
