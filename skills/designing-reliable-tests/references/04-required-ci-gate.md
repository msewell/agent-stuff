# Required CI gate

## Make a valid green explicit

1. Run on the exact PR/merge candidate. In GitHub Actions with merge queue, use both `pull_request` and `merge_group` (`checks_requested`); do not substitute the PR head for the merge group. Keep the required workflow and migration check present independent of path filters. A skipped workflow can leave checks pending; a conditionally skipped job can appear successful. A missing `merge_group` result does not automatically inherit a passing PR check; describe the missing evidence, not an assumed merge-queue outcome. A scoped no-op from another check proves nothing about a required test or migration lane. Do not use `continue-on-error` for required lanes.
2. Have an always-run verifier reconcile the expected job, test and shard identities with first-attempt evidence and the candidate/policy identity. Treat missing, zero-case where cases are required, unexpectedly skipped, cancelled or mismatched results as non-green. Use a policy-owned reporter whose credentials and verifier configuration cannot be changed or accessed by candidate code. Bind evidence to the expected run and candidate; treat candidate-generated reports as untrusted inputs. A workflow rerun counter only guards the same workflow run; a separate run or re-enqueued candidate can evade it without a durable record.
3. Keep an append-only record of the first outcome. An assertion failure, test-owned timeout, or resource leak stays red on that candidate; later retries only add evidence. Classify independently verified platform loss before any verdict as inconclusive; route any authorized bounded fresh attempt through trusted policy without overwriting red. Distinguish superseded candidates in reporting without losing previously observed failures.

## Reject retries and prove the evidence path

Verify retry precedence on the repository’s pinned runner with the probes below. For example, Bun 1.4.4 allows `{ retry: 1 }` to override `--retry=0`: a fail-then-pass can print an assertion failure but exit zero with zero JUnit failures. Do not rely on JUnit, exit codes, or workflow attempt IDs alone. Check test declarations, shared wrappers, preloads and effective config before execution. Prefer a syntax-aware allowlist; reject unresolvable dynamic options rather than accepting a grep-based claim of enforcement. Keep retry-enabled diagnostics outside the required entry point.

Retain attempt-level events when available, or pin the runner, preserve its original stdout/stderr and validate any parser against the runner version. Archive first failure before it can be superseded. Distinguish test attempt, job/shard, workflow attempt, candidate and policy. Fail closed on missing or unrecognized evidence. Limit retention and redact sensitive data.

Run two distinct probes on the same synthetic fail-then-pass fixture: (1) present it as an input to required-suite preflight and assert it is rejected before any test executes; (2) deliberately bypass preflight in a separate diagnostic run and assert that the first failure is preserved and the result cannot grant a required green, even when final JUnit passes. Never add the fixture to normal required discovery. Replace required coverage before merge even if the cause is only in test code. Retire coverage only if review explicitly establishes that the behavior need not block merge. Also probe a skipped migration lane, missing shard and wrong candidate. For the runner-loss path, compare an independently confirmed provisioning failure before any verdict with an unexplained cancellation or missing report; only the confirmed case can qualify for a trusted fresh attempt. A forced abort alone is not evidence of platform loss. For hosted protection, verify the actual protected check; local syntax and shell checks are insufficient.

## Bind deployment to what was tested

Build once when promoting a prebuilt image or bundle. Have integration jobs record the digest they actually exercised; tie source-level checks to the exact candidate and build inputs without claiming that those ran inside the artifact. Record a distinct migration bundle digest when shipped separately. Authorize promotion only when the trusted verdict names the deployed digest, candidate, policy, required manifest and migration baselines/results. Reject a different digest even from the same commit. If signing an attestation, verify the signer, predicate and subject at release; signing binds a claim but does not make untrusted reports true.
