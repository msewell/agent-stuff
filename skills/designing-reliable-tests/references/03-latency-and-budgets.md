# Latency and budgets

1. **Measure the critical path.** Track push and queue entry/start, checkout, install/cache, build, readiness, fixture setup, execution, teardown, upload and final decision. Use the longest dependency path, including queues and stragglers, not the sum of parallel durations. Time test execution separately before changing worker counts. Sum the sequential phases in the same unit; if the quoted total disagrees, state the discrepancy. Label perfect-parallel savings as an upper bound before queue, duplication and straggler costs.
2. **Remove measured work first.** Eliminate redundant builds, installs, browser startup, coverage compilation and fixed waits. Move a test down a layer only if the cheaper test catches the same defect. Reuse immutable binaries or fixture templates whose complete inputs match; allocate independent mutable state. Track clean cache misses, not only warm hits.
3. **Parallelize only after isolation.** Sweep worker and shard counts under CPU, memory, DB connection and I/O caps. Balance by recent durations from one common snapshot. Check that the expected test/project manifest matches the union of shard results exactly once. A job exiting zero is not evidence of nonempty coverage. Confirm the runner’s isolation boundary on the pinned version; Bun 1.4’s default `--parallel` behavior isolates files, not cases or external services.
4. **Select only with a conservative dependency model.** Include runtime SQL/files, config, generated artifacts, lockfiles and environment inputs, not just imports. For unknown graph coverage or base, run the full relevant suite; missing file-dependency edges are a selection risk, not evidence of shared writable state; preserve an always-run core and never select away migration verification. Shadow against full runs and fix any missed failure. Cache a passing test verdict only if the complete action and execution identity is sound; do not cache migration, quarantine, non-hermetic or diagnostic verdicts. Build artifacts may still be cached independently.
5. **Measure the outcome.** Compare p50/p95 push-to-verdict and time to the first actionable failure; separate cold/warm and queue/run cohorts on comparable runner classes and load. Count timeouts and missing runs as SLO misses. Track runner-minutes, first-attempt reliability and any lost or deferred coverage. Before gating on a small timing regression, measure noise with A/A, then run interleaved or paired A/B.

Starter SLOs when none exist: p95 ≤2 seconds for a warm focused local run, ≤15 seconds for the warm local small suite, and ≤5 minutes push-to-verdict for a typical required PR gate. Treat these as starting points, not proof or universal thresholds. Use separate queues/execution objectives, a generous watchdog above normal variance, and hard quotas for controllable work. Establish a representative baseline and review tradeoffs before changing limits; keep any data-scale rehearsal required when migration safety depends on it. Do not invent cache restore times or subtract a centralized build from cold push-to-verdict; it still runs on the critical path unless it is avoided entirely.

For independent setup within one GitHub Actions job, default to sequential steps. If overlap is worth measuring and the platform and validator support native `parallel` groups, overlap setup after dependency installation and wait for all steps before checking readiness. Do not share writable state to gain speed.

**Example:** If a ten-minute gate spends only 45 seconds executing tests, even eliminating test execution entirely saves at most 45 seconds with all else unchanged. Profile the build and remove redundant work or reuse a verified matching artifact. Keep full coverage when runtime fixture dependencies are unknown. Re-measure queue and build setup too; a warm cache or shifting work to another job is not by itself proof of a faster gate.
