# Test design and flake diagnosis

## Design the smallest faithful check

- Choose pure logic or in-process request handling for behavior that needs neither sockets nor a real service. Keep dependency construction at the composition root. In Elysia, build the app without `.listen()` and call `app.handle(new Request('http://test.invalid/…'))`. That checks routing and serialization, not TCP, TLS or proxy wiring.
- Use real, private services only for semantics the smaller boundary cannot expose. Replace live partners with a local double and check its expectations against a provider contract separately. Deny undeclared egress after provisioning; prove the boundary with an attempted prohibited request and an allowed positive control.
- Inject wall time for calendar decisions, monotonic time for elapsed durations, and seeded randomness for generated data. For required property tests, declare a stable seed set and cap samples and shrinking within the lane budget. Rotate seeds in a separate exploration lane; do not let a new seed clear a required failure. Record failing seeds, tool/version and minimized inputs or replay paths, and pin useful counterexamples as regression cases. Freeze time and advance work explicitly; fake time does not drain native I/O or another process. Subscribe before triggering work or await a durable, test-specific condition. For a negative assertion, advance to a defined observation point (e.g., queue drained) rather than waiting a guessed interval.
- Give tests unique writable state and clean up on failure. Bind ports with `0`, then read the bound port. Do not share accounts, mutable global fixtures, or fixed paths. Use an independent oracle: compare unordered results without losing duplicates; impose a stable tie-breaker only if order is contractual.
- Reproduce known interleavings with barriers or a controlled scheduler. With fast-check, record the seed and replay path; use `schedulerFor` for a fixed regression. `scheduleFunction` controls promise-result delivery, not the start of the underlying call or actual DB/OS scheduling. If real interleavings remain free, assert the invariant (e.g., exactly one reservation succeeds), not which caller won.

## Investigate before quarantining

1. Preserve the candidate, stable test ID, runner and versions, fixture identity, first stack/trace, test versus workflow attempt, and relevant seed, order or event schedule. Distinguish product bug, test/harness bug, independently verified platform failure, and unknown; unknown is not green.
2. Reproduce on the original environment first. Compare alone, same-file order, full suite, and parallel run one variable at a time. Bun file isolation does not isolate cases within the file. For an order dependency try victim alone, `A → victim`, and `victim → A` with the same hooks in fresh processes. Bisect the predecessors without changing their relative order. For a failure burst, investigate the shared fixture, runner or service before filing one ticket per test.
3. Fix the mechanism and replay it with a failing negative control and a clean control. Record unexplained failures in qualification runs; do not treat passing repetitions as proof. Zero failures in 100 independent runs still allow roughly a 3% one-sided 95% upper bound on a constant failure probability; correlated runs weaken that inference.
4. If a known flaky test cannot be repaired immediately, use the central quarantine registry. Require stable ID, owner, issue, evidence, expiry and required replacement or an explicit reviewed decision that the risk need not block. Start with seven calendar days unless policy differs. Execute separately and alert before expiry. Fail the policy check on expired entries, not on quarantine assertions. Re-admit after the cause or boundary is fixed and the original trigger and relevant order/concurrency probes pass.

For a legacy suite, prioritize first-attempt visibility and migration verification, cluster common failures, then replace coverage and migrate one test family at a time. Consider a time-capped advisory mutation probe on risky changes: a flipped boundary assertion or suppressed write should fail the intended check; an infrastructure timeout is not a detected defect.
